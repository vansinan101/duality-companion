# Duality Companion: working rules for every Claude on this repo

This repo is the **Duality Companion** (working name), a web character sheet and GM table for Sinan's Daggerheart™ Compatible home game (the Witherwild campaign). It's a sister project of the Clockwork Companion and follows the same protocol, with one difference: **Sinan works on it alone**, so there are no collaborators' branches to respect. Read this whole file before changing anything. When this file and Sinan disagree, ask him.

- **Sinan** owns the repo. He often sends ideas from his phone and can't check stability himself, so nothing reaches the live site untested. Talk to him in plain language, with analogies rather than jargon.
- **Live site:** `https://<owner>.github.io/<repo>/` · **Test site:** the same address + `/dev/` (red DEV ribbon).

## 1. Branches: how work moves

```
feature branch ──PR──▶ Dev ──(tested on /dev/)──PR──▶ main ──▶ live site
```

- **main is production.** Never push to it directly, never force-push it, and merge into it only when Sinan says "release" / "merge to main". It changes only through a pull request from Dev.
- **Dev is the test branch.** Changes reach it through a pull request; check the result on `/dev/`.
- **Never delete Dev**, and never tick "Delete branch" on a pull request whose head is Dev. Deleting it breaks the test site and the publish workflow (the Clockwork repo lost Dev that way once).
- **GitHub enforces this** with the ruleset "Protect main and Dev": no deleting or force-pushing either branch, changes only by pull request with the **check** job green. Sinan, as admin, may bypass it in an emergency, for pull requests only.
- **One branch per feature**, cut from the latest Dev: `sinan/level-up-polish`, `sinan/theme-witherwild`. Small branches are easy to review and to drop.
- When main gets a fix Dev doesn't have, bring it back with a pull request main → Dev so `/dev/` never tests something older than the live site.

## 2. Publishing (don't break this)

- `.github/workflows/pages.yml` runs on every push to **main** or **Dev**. It builds main into the site root and Dev into `/dev/`, both from `src/`, and force-pushes the result to **`gh-pages`**, which GitHub Pages serves.
- **Never edit `gh-pages` by hand**, and never commit built files (`index.html`, `dist/`, `site/`, `sw.js`). The checks fail if you do.
- `firebase-config.js` at the root holds the real Firebase settings (a Firebase web config isn't a secret; the database rules protect the data). **Never overwrite it** with the empty template in `src/web/`.
- Keep `pages.yml` on both main and Dev.

## 3. Source, data and build

**Edit only `src/`** (and `tools/`, `tests/`). Build locally to test:

```
python3 src/build.py                    # dist/duality-companion.html: one file, saves in the browser (previews, claude.ai artifact)
python3 src/build.py --web site --dev   # the website build, as /dev/ gets it
node tests/t_rules.js                   # rules engine against the SRD's own examples
python3 tests/check_repo.py             # repository rules
python3 tests/journey.py dist/duality-companion.html shots 1280   # browser walk-through (also 390)
```

| File in `src/` | What it holds |
| --- | --- |
| `config.js` | The app's name and the licence wording. The name must never contain Darrington Press marks. |
| `icons.js` | Icons from game-icons.net (CC BY 3.0), packed by `tools/build_icons.py` from the list in `tools/icons.txt`. Never edit by hand; credit stays in `ATTRIBUTION.md`. |
| `srd-data.js` | All game content from the **SRD 2.0**. Generated by `tools/build_srd.py`; never edit by hand. |
| `rules.js` | The rules engine `DH`: traits, thresholds, damage, Proficiency, level-ups, rests, dice, gold. No UI; runs in Node. |
| `rules-info.js` | The rules panels shown when a heading is clicked, laid out as light icon lists, equations, scales and examples (part types listed at the top of the file), and the `GLOSSARY` behind the hover cards on rule tokens (Spellcast Roll, ranges, conditions…). App readings are marked `{ note }`. Flavour lines are our own words. |
| `app.js` | The UI (Preact + htm, no build step): storage, switcher, sheet, abilities, gear, story, data, dice dock, companion. |
| `levelup.js`, `genesis.js`, `gm.js` | Level-up wizard; the nine-step character creation; the GM table. |
| `web-backend.js`, `web/` | Website only: sign-in, Firestore, database rules, setup README, settings template. |
| `app.css` | All styling. Themes will live here as `html[data-skin="…"]` blocks, as in Clockwork. |
| `vendor/` | Preact 10.19.3 and htm 3.1.1, built into the page. |

**Regenerating the game data:** `python3 -I tools/build_srd.py <SRD 2.0 markdown> src/srd-data.js <SRD 1.0 JSON folder>` (the third argument tags Hope & Fear content, `hf: 1`, by comparing with SRD 1.0, which holds only the Core Set), then `python3 -I tools/check_srd.py src/srd-data.js <independent SRD text>` must report every value agreeing. Sources are listed in `DATA-NOTES.md`.

## 4. Data: never break a saved character

The live and Dev sites share **one Firestore database**. A character saved by an older version must keep working in a newer one, and the live site must survive data written by Dev.

- **New fields:** default them in `blankCharacter()` and repair them in `normalize()` (`rules.js`). Never assume a field exists.
- **Renaming or removing a field** needs a migration in `normalize()` and a note in the pull request.
- **Derived, not stored:** Evasion, HP and Stress slots, thresholds, Proficiency and trait values are worked out from class, armor, heritage and the recorded `levelups`. Don't store them; add a bonus field or a level-up entry instead. This is the Karma-pool rule of Clockwork in Daggerheart form.
- **Database rules:** `src/web/firestore.rules` is the source. A change only takes effect when pasted into the Firebase console, and it affects the live site at once; say so in the pull request.
- **Testing on `/dev/`:** use a **test table** (a table password nobody plays on), never the campaign table.

## 5. Licence guardrails (DPCGL 2.0)

- Game content comes **only from the SRD 2.0** (Public Game Content). Never paste text from the core rulebook or other books.
- **No Darrington Press marks in the app's name or title**; "Daggerheart" appears only as "Daggerheart™ Compatible" in descriptive text. No official logos, art or trade dress.
- Keep the attribution in `config.js` and `ATTRIBUTION.md` (the checks look for it) and the "unofficial, not affiliated" line.
- The site is a **private home-game tool**: keep `noindex`/`robots.txt`, don't link it publicly. Going public needs written permission from Darrington Press first (`ATTRIBUTION.md`).
- **Witherwild** (campaign frame) mechanics stay behind the GM's table switch and must be removable for any public build.

## 6. Design rules (from Clockwork, agreed with Sinan)

- **Less is more.** The fewest controls that do the job.
- **Plain language** everywhere: short sentences, no jargon, no internal names.
- **Mouse:** left-click adds, marks or raises; right-click clears or lowers; long-press does the right-click on phones. Hover says what a click will do.
- **Headings with rules behind them** open the side panel; add topics to `rules-info.js`, not long inline help.
- **SRD first, house rules over the SRD.** When the SRD is unclear, don't invent: ask Sinan, and mark the app's reading with a `{ note }`.
- Every screen works at **390 px** wide with no sideways scrolling, and drop-downs stay readable.
- **Themes come last** (Sinan's call): build features on the plain look first.

## 7. Before you open a pull request

1. Branch from the latest Dev; merge Dev in again before opening the PR.
2. Run the four commands in §3. All must pass.
3. Look at the screenshots at 1280 and 390 px, in light and dark, for the screens you changed.
4. Commit with a message saying what changed for the player or GM.
5. Open the PR into **Dev**, describing in plain words what changed and how to test it on `/dev/`.
6. After Sinan has tried it on `/dev/` and says "release", open the PR **Dev → main**. Never tick "Delete branch" on it.
